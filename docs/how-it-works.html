Panes

Dockable, splittable, detachable panels — like an IDE — built on Flutter's experimental multi‑window APIs plus a thin native AppKit layer on macOS.

Step 1 · The constraint

Multi‑window is experimental

Everything hangs off Flutter's windowing APIs, which only exist on the main/master channel and are @internal. Three hard facts shaped every decision:

  • The APIs live in a private file — you import it and silence two analyzer rules.
  • On macOS you cannot create a borderless window through Flutter (decorated:false throws) — so "no title bar" is done natively.
  • Regular windows expose no screen position — so drag‑back‑to‑snap needs native window tracking.
// every file that touches the windowing APIs starts with:
// ignore_for_file: invalid_use_of_internal_member
// ignore_for_file: implementation_imports
import 'package:flutter/src/widgets/_window.dart';
Step 2 · Turn it on

Enable the feature, then run

Windowing is a build‑time framework flag — it can't be set via --dart-define. Flip it once with flutter config:

# once
fvm flutter config --enable-windowing

# then, every time
fvm flutter run -d macos

Requires a master‑channel Flutter (the demo pins one via fvm).

Step 3 · The macOS runner

Run a headless engine

The default macOS template attaches a FlutterViewController at launch. The first time Dart creates a window the engine calls enableMultiView, which aborts if a view controller already exists:

*** reason: 'Multiview can only be enabled before
            adding any view controllers.'

Fix: the runner runs a headless FlutterEngine in applicationDidFinishLaunching and lets Dart create every window. The storyboard's auto‑instantiated MainFlutterWindow is removed.

override func applicationDidFinishLaunching(_ n: Notification) {
  engine = FlutterEngine(name: "panes", project: nil)
  engine?.run(withEntrypoint: nil)   // no view controller yet
}
Step 4 · How windows compose

One tree, many views

runWidget renders a WindowManager, which renders every registered window — the main one included — as a sibling view via ViewCollection. All in one isolate, so every window shares one PanelManager.

runWidget(PanelScope(            // shared state, above WindowManager
  manager: manager,
  child: WindowManager(            // hosts every OS window
    initialWindows: [WindowEntry(
      controller: WindowController(size: Size(1180, 760)),
      builder: (_) => AppShell(home: PanelDock()),  // any WidgetsApp
    )],
  ),
));
  • Not dependent on Material — drop PanelDock into any app shell; its look comes from PanelTheme, not Material.
  • PanelScope sits above WindowManager so detached sibling‑view windows can still read the shared manager.

Step 7 · Drag interactions

Drag a tab — it knows where it'll land

  • Drag within the tab strip → reorder (an accent insertion line marks the slot).
  • Drop on a group's center → add as a tab.
  • Drop on a group's edge → split into a new group beside it (with a live preview).
  • Drop on an empty region edge → create the first group there.
  • Drop outside the window → tear off into a floating OS window.
  • Or skip the mouse: focus a group and press ⌘\ to split / ⌘⇧\ to merge.

Step 8 · The native layer

AppKit does what Flutter can't

A dart:ffi bridge connects Dart and Swift — forward calls via ffigen bindings into Swift @_cdecl functions, reverse drag/drop events via NativeCallable pointers — for things Flutter can't do on macOS:

  • Hide the title bar: a detached window is matched by a hidden title token, then styled — fullSizeContentView, transparent titlebar, hidden traffic lights, isMovableByWindowBackground.
  • Open where you are: it's positioned at the mouse and moved to the active Space, so it doesn't pop back to the original desktop.
  • Drag‑back snapping: a 60 fps timer streams the live pointer + window frames and detects release via NSEvent.pressedMouseButtons (a leftMouseUp monitor is swallowed by the window‑drag loop).

Dart maps the pointer onto the dock and shows a single target preview only while it's over the main window — then redock() snaps it in.

Step 9 · Make it yours

No Material tint — pure PanelTheme

The dock paints from a Material‑independent PanelTheme (neutral light/dark by default), so there's no surface tint. Tabs can be rendered however you like.

PanelManager(config: PanelDockConfig(
  lightTheme: PanelTheme.light(),
  darkTheme:  PanelTheme.dark(),
  tabBuilder: (context, spec) => MyTab(    // arbitrary tabs
    title: spec.descriptor.title,
    selected: spec.selected, theme: spec.theme,
  ),
));
Step 10 · Remember the layout

Pluggable persistence

Implement PanelStorage and the manager auto‑saves (debounced) on every change; restore() reloads it on startup.

class MyStorage implements PanelStorage {
  FutureOr<Map<String, Object?>?> read() => /* load */;
  FutureOr<void> write(Map<String, Object?> m) => /* save */;
}

final manager = PanelManager(config: PanelDockConfig(storage: MyStorage()))
  ..registerPanel(/* … */);
await manager.restore();   // applies the saved layout
Step 11 · Keyboard‑driven

Split & merge with the keyboard

Splitting/merging is exposed as Actions & Intents acting on the focused group (a group focuses on click and shows an accent border).

⌘ \  split the focused panel    ⌘ ⇧ \  merge it back

Shortcuts(
  shortcuts: defaultPanelShortcuts(),
  child: Actions(
    actions: panelActions(manager),
    child: const Focus(autofocus: true, child: PanelDock()),
  ),
);
That's the whole thing

Flutter windows + a little Swift

Experimental multi‑window Flutter gives real OS windows in one shared isolate; a thin AppKit layer supplies the borderless chrome and pointer‑tracked docking Flutter can't reach yet. Everything else — splits, theming, persistence, shortcuts — is plain Dart.
